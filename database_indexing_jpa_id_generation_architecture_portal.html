SECTION 1 STORAGE FUNDAMENTALS

What Does Database Indexing Mean Architecturally?

When a database table has no index (known as a Heap Table), new rows are appended wherever free space exists across fixed-size disk pages (typically 8 KB in PostgreSQL or 16 KB in MySQL InnoDB). Filtering on an unindexed column forces the storage engine to execute a Full Table Scan—reading every page from disk into RAM and inspecting every row sequentially at O(N) cost.

Database Indexing creates a persistent, ordered auxiliary data structure—most commonly a balanced multi-way search tree (B+Tree)—that maps column values to the physical or logical locations of rows on disk, reducing lookup complexity from O(N) to logarithmic O(log_b N) (typically 3 to 4 page reads even for 100 million rows).

Unindexed Heap Table O(N) SCAN

Reads every 8KB/16KB page sequentially. Fast for blind appends, but catastrophic for selective WHERE, JOIN, or ORDER BY queries.

B+Tree Indexed Seek O(log_b N) SEEK

With a branching factor (fan-out) of 300–500 keys per page, a B+Tree of depth 3–4 narrows 100M rows down to the exact leaf page in 3–4 buffer reads.

The Write Trade-Off WRITE AMPLIFICATION

Every INSERT, DELETE, or indexed UPDATE must mutate both the table and every affected index tree, potentially triggering 50/50 leaf page splits.

STORAGE ENGINE ARCHITECTURE

Clustered Index vs. Non-Clustered (Secondary) Index

How an index leaf node connects to the underlying row depends on the RDBMS engine.

A. Clustered Index (1 Per Table Max)

LEAF = DATA ROW

In a Clustered Index (default PRIMARY KEY in MySQL InnoDB and SQL Server), the leaf nodes of the B+Tree are the actual physical data pages sorted in primary key order.

[Root Page #1: Keys < 500 | ≥ 500]
↳ [Branch Page #3: Keys 500..750]
↳ [Leaf Data Page #12]: Contains FULL Row (id: 520, name: 'Ana', salary: 95000)

Why only 1 Clustered Index per table? Because physical rows on disk can only be sorted in one physical sequence.

B. Non-Clustered (Secondary) Index

LEAF = KEY + POINTER

A separate B+Tree sorting only the indexed column(s). Each leaf entry stores the indexed key plus a pointer to find the rest of the row:

[Secondary Root: idx_users_email]
↳ [Index Leaf Page #42: 'ana@corp.io' → Pointer]
↳ Pointer Fetch: Reads Heap Tuple ctid(105,4) in PG, or traverses Clustered PK in InnoDB

PostgreSQL Note: In PostgreSQL, all indexes (even the Primary Key) are Non-Clustered secondary indexes pointing to ctid page/slot offsets in the Table Heap.

SECTION 2A SHOWING 9 OF 9 TYPES

Database Table Indexing Types

Use the capability filter dropdown to find which index structure supports specific SQL operators and workloads.

Index Type Complexity & Scope Internal Structure & How It Works Supported Queries & Trade-Offs
1. B-Tree / B+Tree O(log_b N) DEFAULT Balanced multi-way search tree. Internal pages route keys; doubly-linked leaf pages hold sorted keys and row pointers. Supports: Equality (=), Ranges (>, <, BETWEEN), prefix LIKE 'abc%', and zero-sort ORDER BY. Default in PG, MySQL, Oracle, SQL Server.
2. Hash Index O(1) EQUALITY Maps a 32/64-bit hash digest of the indexed column into hash buckets containing tuple pointers. Supports: Strict equality (WHERE token = 'xyz') only. Cannot support range scans, sorting, or prefix matching.
3. GIN (Inverted Index) MULTI-VALUE / JSONB Splits composite values (JSONB keys, array elements, text lexemes) and maps each token to a posting list of Row IDs. Supports: PostgreSQL JSONB containment (@>, ?), array overlap (&&), and Full-Text Search (@@).
4. GiST / R-Tree GEOSPATIAL / RANGES Balanced tree partitioning multi-dimensional bounding boxes and geometric intervals. Supports: PostGIS distance/containment (ST_DWithin, polygon overlap), range types, and exclusion constraints.
5. BRIN (Block Range) 99.9% SMALLER Stores only the min and max values per contiguous block of 128 disk pages (~1 MB). Supports: Range scans on multi-terabyte append-only time-series tables where rows are physically ordered by timestamp on disk.
6. Bitmap Index OLAP BITWISE Maintains a compressed bit array (0s and 1s) for each distinct value; combines multiple predicates via CPU bitwise AND / OR. Supports: Analytical queries combining multiple low-cardinality filters. High write-lock contention if stored persistently in OLTP.
7. Composite Index MULTI-COLUMN KEY Concatenates multiple columns (A, B, C) into a single hierarchical sort key inside a B+Tree. Supports: Queries matching the Leftmost Prefix (A), (A, B), or (A, B, C) following the ESR Rule.
8. Covering Index (INCLUDE) 0 HEAP READS Appends non-searchable payload columns strictly to the B+Tree leaf pages (omitting them from upper branch nodes). Supports: Index-Only Scans—returns all SELECT columns directly from the index leaf without reading the Table Heap.
9. Partial & Expression FILTERED / COMPUTED Indexes only rows matching a WHERE clause (e.g., WHERE status = 'ACTIVE') or a function output (LOWER(email)). Supports: Targeted queries on skewed tables (shrinking index size by 80–95%) and case-insensitive SARGable lookups.
SECTION 2B

How Many Columns May Be Indexed On?

There is a major difference between the RDBMS Engine Hard Limit (compile-time constants) and the Practical Architectural Limit (3 to 4 columns).

1. RDBMS Engine Hard Limits

Database Engine Max Columns / Composite Index Max Key Byte Size
PostgreSQL 32 COLUMNS (INDEX_MAX_KEYS) ~2,704 bytes (⅓ of 8KB page)
MySQL (InnoDB) 16 COLUMNS (Max 64 indexes/table) 3,072 bytes (DYNAMIC row)
SQL Server 32 KEY COLS (+ 1,023 INCLUDE) 900B (Clustered) / 1,700B (NC)
Oracle 32 COLUMNS (30 for Bitmap) ~75% of DB block size
SQLite 2,000 COLUMNS Bounded by 4KB page size

2. Why the Practical Limit is 3 to 4 Key Columns

A. The Leftmost Prefix Rule SORT HIERARCHY

An index on (A, B, C) sorts first by A, breaks ties by B, then C. A query filtering only on B cannot traverse the tree directly.

B. The ESR Rule (Equality → Sort → Range) RANGE STOPPAGE

The first column with a range condition (>, <, BETWEEN) stops B+Tree key lookup for all subsequent columns to its right. Order composite columns as: Equality first, Sort second, Range last.

C. Page Fan-Out Degradation PAGE BLOAT

Adding 6+ columns widens every key tuple, reducing how many keys fit in an 8KB/16KB page and making the tree deeper. Place extra SELECT columns in INCLUDE (...) instead.

JPA Auto ID Generation Strategies: Pros, Cons & Use Cases

Your choice of @GeneratedValue governs whether Hibernate can execute JDBC Batch Inserts and whether Primary Key inserts append cleanly to the B+Tree or cause 50/50 Leaf Page Splits.

JPA Strategy JDBC Batching Round-Trips (1,000 Rows) B+Tree PK Page Splits Best Production Use Case
1. SEQUENCE (pooled-lo) SUPPORTED 20 Seq + 20 Batch = 40 ZERO (Right-Append) Gold standard for PostgreSQL, Oracle, SQL Server, DB2
2. IDENTITY DISABLED BY SPEC 1,000 immediate inserts ZERO (Right-Append) Simple single-row CRUD on MySQL InnoDB
3. UUIDv7 / TSID (Time) SUPPORTED (Client) 0 ID + 20 Batch = 20 ZERO (Time-Ordered) Distributed systems, microservices & MySQL bulk batching
4. UUID (v4 Random) SUPPORTED (Client) 0 ID + 20 Batch = 20 SEVERE 50/50 SPLITS Avoid as Clustered PK; upgrade to UUIDv7
5. TABLE ROW-LOCK BOTTLENECK 20–1000 locked TXNs ZERO (Sequential) Legacy fallback only — avoid due to HikariCP pool starvation
6. AUTO DIALECT DEPENDENT Varies by RDBMS DIALECT DEPENDENT Prototyping only; declare strategy explicitly in production

1. GenerationType.SEQUENCE (with pooled-lo)

RELATIONAL GOLD STANDARD

Uses a native, lock-free database sequence combined with Hibernate's client-side pooled-lo optimizer. When allocationSize = 50, Hibernate fetches 1 sequence value from the database and computes 50 unique IDs in JVM memory before needing another database call.

Pros
  • Supports JDBC Batching: IDs are known before INSERT, allowing Hibernate to batch 50–100 rows per network round-trip.
  • Zero B+Tree Page Splits: Monotonically increasing 8-byte BIGINT appends strictly to the rightmost leaf page (~96% fill factor).
Cons
  • Not natively supported by MySQL InnoDB (falls back to slow TABLE generator).
  • Can leave harmless numeric gaps in IDs on JVM restart or transaction rollback.
Best Use Case: High-throughput OLTP services and bulk batch persistence on PostgreSQL, Oracle, SQL Server, or DB2. 
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
@SequenceGenerator(name = "order_seq", sequenceName = "orders_id_seq", allocationSize = 50)
private Long id;

2. GenerationType.IDENTITY

DISABLES JDBC BATCHING

Relies on an auto-incrementing table column (AUTO_INCREMENT in MySQL, GENERATED ALWAYS AS IDENTITY in PostgreSQL) where the ID is generated only during physical INSERT execution.

Pros
  • Sequential B+Tree Appends: 8-byte monotonic BIGINT keeps MySQL InnoDB Clustered Primary Keys compact and unfragmented.
  • Simple DDL setup with zero sequence step mismatches.
Cons
  • Disables Hibernate JDBC Batching: Because JPA requires the entity ID immediately inside em.persist(entity), Hibernate must execute the INSERT immediately instead of buffering it until flush.
Best Use Case: Standard single-row CRUD APIs on MySQL InnoDB where bulk inserts are either rare or handled via JdbcTemplate. 
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id; // Executes immediate INSERT on persist(); bypasses hibernate.jdbc.batch_size

3. UUIDv7 (RFC 9562) / Time-Sorted TSID

DISTRIBUTED + B+TREE SAFE

Replaces random UUIDv4 with a 48-bit Unix epoch millisecond timestamp prefix followed by 74 random bits. Generated client-side in the JVM before touching the database.

Pros
  • Full JDBC Batching Everywhere: Works on MySQL, PostgreSQL, and multi-region shards with zero DB round-trips for ID allocation.
  • Zero Mid-Tree Page Splits: Time-ordered prefix ensures new rows append to the rightmost B+Tree leaf (~94% fill factor).
Cons
  • 16 bytes wide (twice the size of 8-byte BIGINT); must be stored as native uuid or BINARY(16), never VARCHAR(36).
  • Encodes creation timestamp to millisecond precision.
Best Use Case: Microservices, offline-first clients, event-driven architectures, and MySQL InnoDB apps requiring fast JDBC batch inserts. 
@Id
@UuidGenerator(style = UuidGenerator.Style.TIME) // Or custom RFC 9562 UUIDv7 @IdGeneratorType
@Column(columnDefinition = "uuid", updatable = false, nullable = false)
private UUID id;

4. GenerationType.UUID (Random UUIDv4)

CAUSES B+TREE PAGE SPLITS

Generates 122 bits of cryptographic randomness (`UUID.randomUUID()`). While convenient for distributed creation, it has severe storage engine consequences when used as a B+Tree Primary Key.

Pros
  • Supports JDBC Batching & Distributed Generation: Zero coordination needed across servers.
  • Non-enumerable in public URLs.
Cons
  • Severe 50/50 B+Tree Leaf Page Splits: Every insert lands in a random historical page, splitting full pages in half, dropping fill factor to ~55%, and thrashing Buffer Pool RAM.
Best Use Case: Unindexed correlation tokens or secondary external IDs. Replace with UUIDv7 for Primary Keys. 
@Id
@GeneratedValue(strategy = GenerationType.UUID) // Defaults to random UUIDv4 -> fragments B+Tree leaves
private UUID id;

5. GenerationType.TABLE

LOCK & POOL STARVATION

Emulates a sequence using a standard database table (`hibernate_sequences`) updated via `SELECT ... FOR UPDATE` inside a separate isolated physical transaction (`REQUIRES_NEW`).

Pros
  • Works on legacy databases without native sequence support.
Cons
  • Row-Lock Contention & HikariCP Pool Deadlock: Every thread holds 1 connection for its main transaction and demands a 2nd connection to lock and increment the sequence row.
@Id
@GeneratedValue(strategy = GenerationType.TABLE, generator = "tbl_gen")
@TableGenerator(name = "tbl_gen", table = "hibernate_sequences", allocationSize = 50)
private Long id;

6. GenerationType.AUTO

IMPLICIT DIALECT DEFAULT

Delegates the strategy decision to the active Hibernate SQL Dialect. Picks `SEQUENCE` on PostgreSQL/Oracle, `UUID` for `java.util.UUID` fields, and historically picked `TABLE` on MySQL in Hibernate 5.

Pros
  • Convenient for quick prototypes and vendor-agnostic test demos.
Cons
  • Hides allocation size and physical generator behavior; always prefer explicit `@SequenceGenerator` or `UUIDv7` in production.
@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;

How to Test & Prove JPA ID and Indexing Pros/Cons

Use these three deterministic verification blueprints to prove JDBC batching behavior, measure physical B+Tree page splits on disk, and expose connection pool starvation under concurrency.

TEST BLUEPRINT 1 • JDBC BATCHING

Proving SEQUENCE (pooled-lo) vs. IDENTITY Round-Trips with Datasource-Proxy

JUnit 5 + net.ttddyy:datasource-proxy

Standard Hibernate SQL logs print every logical addBatch() call, hiding whether statements were actually sent over the network in batches. Wrapping your DataSource with datasource-proxy lets your automated test assert exact wire-level executions: 

@SpringBootTest(properties = {
    "spring.jpa.properties.hibernate.jdbc.batch_size=25",
    "spring.jpa.properties.hibernate.order_inserts=true"
})
class JpaBatchingProofTest {

    @Autowired private OrderSequenceRepository sequenceRepo; // GenerationType.SEQUENCE (allocationSize = 50)
    @Autowired private OrderIdentityRepository identityRepo; // GenerationType.IDENTITY

    @BeforeEach
    void clearCounts() {
        QueryCountHolder.clear();
    }

    @Test
    @Transactional
    void sequencePooledLo_batches100EntitiesInto4JdbcExecutions() {
        var orders = IntStream.rangeClosed(1, 100).mapToObj(OrderSequence::new).toList();
        sequenceRepo.saveAllAndFlush(orders);

        // 100 rows / allocationSize(50) = 2 sequence calls
        assertThat(QueryCountHolder.getGrandTotal().getSelect()).isEqualTo(2);
        // 100 rows / batch_size(25) = 4 batched network executions!
        assertThat(QueryCountHolder.getGrandTotal().getInsert()).isEqualTo(4);
    }

    @Test
    @Transactional
    void identityStrategy_disablesBatchingAndExecutes100IndividualInserts() {
        var orders = IntStream.rangeClosed(1, 100).mapToObj(OrderIdentity::new).toList();
        identityRepo.saveAllAndFlush(orders);

        // Proof of IDENTITY con: 100 separate network round-trips!
        assertThat(QueryCountHolder.getGrandTotal().getInsert()).isEqualTo(100);
    }
}
TEST BLUEPRINT 2 • B+TREE FRAGMENTATION & FILL FACTOR

Measuring 50/50 Page Splits (UUIDv4 vs. UUIDv7 vs. BIGINT SEQUENCE)

PostgreSQL pgstattuple Extension

Use PostgreSQL's built-in pgstatindex() diagnostic function after inserting 250,000 rows to inspect the physical B+Tree leaf fill factor (avg_leaf_density) and out-of-order page splits (leaf_fragmentation): 

CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT
    idx_name,
    pg_size_pretty(index_size)          AS index_size,
    leaf_pages,
    round(avg_leaf_density::numeric, 1) AS avg_fill_factor_pct,
    round(leaf_fragmentation::numeric, 1) AS page_split_fragmentation_pct
FROM (
    SELECT '1. BIGINT SEQUENCE' AS idx_name, (pgstatindex('orders_seq_pkey')).*
    UNION ALL
    SELECT '2. UUIDv7 (Time-Ordered)',       (pgstatindex('orders_uuidv7_pkey')).*
    UNION ALL
    SELECT '3. UUIDv4 (Random)',             (pgstatindex('orders_uuidv4_pkey')).*
) s;

-- EMPIRICAL BENCHMARK RESULT (250,000 ROWS):
-- idx_name                 | index_size | leaf_pages | avg_fill_factor_pct | page_split_fragmentation_pct
-- -------------------------+------------+------------+---------------------+------------------------------
-- 1. BIGINT SEQUENCE       | 5,480 kB   | 683        | 90.1 %              |  0.0 % (Sequential Right-Append)
-- 2. UUIDv7 (Time-Ordered) | 7,520 kB   | 938        | 90.0 %              |  0.0 % (Sequential Right-Append)
-- 3. UUIDv4 (Random)       | 11,450 kB  | 1,429      | 58.2 %              | 49.6 % (Severe 50/50 Page Splits!)
TEST BLUEPRINT 3 • CONCURRENCY & POOL STARVATION

Exposing GenerationType.TABLE HikariCP Deadlock Under Concurrent Load

Java 21 Virtual Threads + HikariCP

Because GenerationType.TABLE requires a second isolated database connection (Propagation.REQUIRES_NEW) to lock and increment the counter row in hibernate_sequences, running 12 concurrent transactions against a 10-connection pool immediately starves HikariCP: 

@Test
void tableGenerator_starvesConnectionPoolWhenConcurrentThreadsExceedHalfPoolSize() {
    // HikariCP maximum-pool-size = 10
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        var tasks = IntStream.range(0, 12)
            .<Callable<Void>>mapToObj(i -> () -> {
                invoiceTableService.createInvoiceInTransaction("INV-" + i);
                return null;
            }).toList();

        // Each thread holds 1 connection and blocks waiting for a 2nd connection to increment TABLE ID:
        assertThatThrownBy(() -> {
            for (var f : executor.invokeAll(tasks)) f.get();
        }).hasRootCauseMessageContaining("Connection is not available, request timed out");
    }
}
