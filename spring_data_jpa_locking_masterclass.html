JPA Annotation / Hint Generated SQL Lock Behavior Customer & Refund Use Case
@Lock(PESSIMISTIC_WRITE) SELECT ... FOR UPDATE Acquires exclusive row lock. Forces concurrent writers & locking readers to queue up until commit. Two threads deducting a refund from the same Customer.balance (takes 20s+ serially instead of 10s).
@Lock(PESSIMISTIC_READ) SELECT ... FOR SHARE Acquires shared lock. Multiple readers run in parallel (~10s), but blocks any writer from modifying the row. Running a 10s compliance report on Customer while blocking a rogueWriter from changing status/balance.
@QueryHint(lock.timeout = "-2") SELECT ... FOR UPDATE SKIP LOCKED Worker Queue: Silently ignores locked rows during index scan and locks the next unlocked row. Worker 1 & Worker 2 polling PENDING rows in the Refund table simultaneously without blocking.
@QueryHint(lock.timeout = "0") SELECT ... FOR UPDATE NOWAIT Fail-Fast: Refuses to wait even 1ms. Throws PessimisticLockingFailureException immediately if locked. Admin attempting to edit a Customer currently locked by a refund settlement job.
@QueryHint(lock.timeout = "3000") SET LOCAL lock_timeout = 3000 Bounded Wait: Blocks thread up to 3,000ms (3 seconds) waiting for the lock before aborting with exception. API request updating Customer willing to wait max 3 seconds before failing gracefully.
@Version (Standard Optimistic) UPDATE ... WHERE id=? AND version=? No DB lock during read. Detects concurrent writes atomically at flush time via updated row count (0 rows = crash). Two admins editing Customer profile or background workers updating balance with @Retryable.
@Lock(LockModeType.OPTIMISTIC) SELECT version FROM customer WHERE id=? Forces a commit-time version check on a read-only parent entity even when the parent itself was not updated. Ensuring Customer is still ACTIVE when inserting a child Refund (where @Version alone fails!).
