KRaft Architecture, Networking Mechanics & Production Topologies

What is KRaft and Why Does It Matter?

Core Paradigm Shift

KRaft (Kafka Raft Metadata Mode) is the modern consensus protocol built directly into Apache Kafka to manage metadata without depending on external tools.

Why KRaft? (The "Why")

  • ZooKeeper Elimination: Historically, Kafka relied on Apache ZooKeeper to store cluster metadata and elect controllers. This introduced a separate distributed system to manage, scale, and secure. KRaft embeds metadata management natively inside Kafka.
  • Massive Scalability: Metadata synchronization in ZooKeeper choked when clusters scaled to millions of partitions. KRaft handles metadata via an event-driven Raft quorum log, allowing clusters to scale effortlessly to millions of partitions with near-instantaneous failover times.
  • Simpler Operations: You no longer need to run two separate clusters (ZooKeeper + Kafka). A single Kafka binary handles both storage and consensus.

Listeners, Advertised Listeners & Protocol Maps

Networking in Kafka is notoriously tricky because clients establish an initial connection to one port, but receive a metadata redirect telling them where to connect for specific partitions. Understanding the mapping is essential when bridging Docker and host machines.

1. KAFKA_LISTENERS (The Binding Address)

Defines the actual network interfaces and ports the Kafka broker binds to inside the container to listen for incoming TCP connections. Setting it to PLAINTEXT://0.0.0.0:9092 means the broker accepts traffic on port 9092 from any network interface inside the container container network.

2. KAFKA_ADVERTISED_LISTENERS (The Redirect Address)

This is the address the broker broadcasts back to clients when they request cluster metadata. If a Spring Boot application runs on your local host machine outside Docker, the advertised listener must be PLAINTEXT://localhost:9092. If it incorrectly advertised kafka:9092, your host machine would throw an UnknownHostException.

3. KAFKA_LISTENER_SECURITY_PROTOCOL_MAP

Maps logical listener names to security protocols. For example, PLAINTEXT:PLAINTEXT tells Kafka that the listener named PLAINTEXT uses unencrypted plaintext communication. In production, you would map secure channels like SSL:SSL or SASL_PLAINTEXT:SASL_PLAINTEXT.

4. KAFKA_CONTROLLER_LISTENER_NAMES

Designates which internal listener name is reserved specifically for KRaft quorum communication between controller nodes (e.g., CONTROLLER).

Single-Node KRaft Docker Compose

A modern, production-ready local setup using KRaft mode (ZooKeeper-less), recommended as the default for Apache Kafka. Includes Kafka UI for cluster visualization.

version: '3.8'
services:
  kafka:
    image: apache/kafka:latest
    container_name: kafka
    ports:
      - "9092:9092"
    environment:
      # KRaft mode settings
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: 'broker,controller'
      KAFKA_CONTROLLER_QUORUM_VOTERS: '1@localhost:9093'
      # Listeners configuration
      KAFKA_LISTENERS: 'PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093'
      KAFKA_ADVERTISED_LISTENERS: 'PLAINTEXT://localhost:9092'
      KAFKA_CONTROLLER_LISTENER_NAMES: 'CONTROLLER'
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: 'PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT'
      # Topic default configurations
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_LOG_DIRS: '/var/lib/kafka/data'
    volumes:
      - kafka_data:/var/lib/kafka/data

  kafka-ui:
    image: provectuslabs/kafka-ui:latest
    container_name: kafka-ui
    ports:
      - "8080:8080"
    environment:
      DYNAMIC_CONFIG_ENABLED: 'true'
      KAFKA_CLUSTERS_0_NAME: 'local-cluster'
      KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: 'kafka:9092'

volumes:
  kafka_data:

Multi-Node (3-Broker) KRaft Cluster

To form a multi-broker cluster, nodes share a unique CLUSTER_ID and cross-reference each other in KAFKA_CONTROLLER_QUORUM_VOTERS.

version: '3.8'
services:
  kafka-1:
    image: apache/kafka:latest
    container_name: kafka-1
    ports:
      - "9092:9092"
    environment:
      CLUSTER_ID: '4L62xdwCQKWvZs96A39vGA'
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: 'broker,controller'
      KAFKA_CONTROLLER_QUORUM_VOTERS: '1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093'
      KAFKA_LISTENERS: 'PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093'
      KAFKA_ADVERTISED_LISTENERS: 'PLAINTEXT://localhost:9092'
      KAFKA_CONTROLLER_LISTENER_NAMES: 'CONTROLLER'
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: 'PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT'
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 3
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 2
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 3
    volumes:
      - kafka1_data:/var/lib/kafka/data

  kafka-2:
    image: apache/kafka:latest

Broker (The Worker) vs. Controller (The Boss)

In KRaft mode, nodes can be co-located or isolated. Their functional boundaries are distinct:

Feature Broker (The Worker) Controller (The Boss)
Primary Role Handles message reads, writes, and local log storage. Manages cluster metadata, state, and coordination.
Client Interaction Talks directly to Producers and Consumers. Talks only to Brokers (Clients do not connect here).
Scaling Scales horizontally (tens or hundreds of nodes). Operates as a strict quorum (typically 3 or 5 nodes).
Topology Mode Co-located (broker,controller) for local dev; isolated in production to protect metadata performance. Co-located (broker,controller) for local dev; isolated in production.
