Data Governance: Schema Registry & Avro

In a microservices architecture, topics act as APIs. If a producer changes the JSON structure of an event, consumers will break. The Confluent Schema Registry combined with Apache Avro enforces strict contracts on your data streams.

1. The Avro Contract (.avsc)

Instead of POJOs, you define schemas. The Avro Maven plugin automatically generates the Java classes during the build process.

{
  "namespace": "com.example.events",
  "type": "record",
  "name": "UserCreated",
  "fields": [
    { "name": "userId", "type": "string" },
    { "name": "email", "type": "string" },
    { "name": "age", "type": ["int", "null"], "default": null } // Backward compatible change
  ]
}

2. Spring Boot Producer Configuration

The producer validates the object against the Schema Registry before publishing. If the schema is incompatible, it throws an exception locally, preventing corrupt data from entering the topic.

spring:
  kafka:
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
    properties:
      schema.registry.url: http://localhost:8081
      auto.register.schemas: false # Force CI/CD to register schemas, not apps

3. Target Outcome

You achieve Forward and Backward Compatibility. You can safely deploy new versions of producers or consumers independently without coordinating downtime, as the Schema Registry mathematically guarantees the new schema will not break downstream systems.

Scatter-Gather & Request-Reply Pattern

Kafka is inherently asynchronous. However, edge cases exist where a REST API needs a synchronous response, but the processing must happen via decoupled Kafka microservices. We achieve this using Spring's ReplyingKafkaTemplate.

1. Architecture Concept

  • The API gateway publishes a message to request-topic and includes a dynamically generated correlationId and a reply-topic header.
  • The gateway thread blocks (with a timeout).
  • The worker service consumes the request, processes it, and publishes the result to the reply-topic, copying the correlationId.
  • The gateway matches the correlationId and resumes the HTTP thread.

2. The Synchronous Gateway (Producer)

@RestController
public class OrderGateway {
    private final ReplyingKafkaTemplate<String, OrderReq, OrderRes> template;

    @PostMapping("/orders")
    public ResponseEntity<OrderRes> createOrder(@RequestBody OrderReq req) throws Exception {
        ProducerRecord<String, OrderReq> record = new ProducerRecord<>("orders-req", req);
        
        // Sends and blocks waiting for the exact correlation ID on the reply topic
        RequestReplyFuture<String, OrderReq, OrderRes> future = template.sendAndReceive(record);
        
        ConsumerRecord<String, OrderRes> response = future.get(10, TimeUnit.SECONDS);
        return ResponseEntity.ok(response.value());
    }
}

3. The Worker (Consumer)

@Service
public class OrderWorker {

    @KafkaListener(topics = "orders-req")
    @SendTo // Automatically routes the return value to the 'reply-topic' header
    public OrderRes processOrder(OrderReq request) {
        // Complex business logic
        return new OrderRes(request.getId(), "APPROVED");
    }
}

Kafka Streams: Stateful Processing & Windowing

Standard consumers process one event at a time (stateless). Kafka Streams allows you to process data over time, joining multiple topics, and aggregating data into state stores (RocksDB) local to your application.

1. Use Case: Real-Time Fraud Detection

Requirement: Detect if a user attempts more than 5 transactions within a 1-minute window.

2. Spring Boot Streams Implementation

@Configuration
@EnableKafkaStreams
public class StreamConfig {

    @Autowired
    public void buildPipeline(StreamsBuilder builder) {
        KStream<String, Transaction> transactions = builder.stream("tx-topic");

        transactions
            .groupByKey() // Group by userId
            .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
            .count() // Stateful operation! Backed by local RocksDB
            .filter((windowedUserId, count) -> count > 5)
            .toStream()
            .map((windowedId, count) -> new KeyValue<>(windowedId.key(), "FRAUD_ALERT"))
            .to("fraud-alerts-topic");
    }
}

3. Target Outcome

Your Spring Boot application is now a real-time stream processing engine. It requires no external database to track the counts; the state is maintained efficiently on the JVM disk and backed up automatically to Kafka changelog topics for fault tolerance.

CQRS & Event Sourcing Architecture

Command Query Responsibility Segregation (CQRS) separates the write model (Commands) from the read model (Queries). Event Sourcing means your source of truth is a log of events, not the current state.

Interactive CQRS Flow

Click "Submit Command" to append an event to the Event Store (Kafka). The Projection Engine consumes this event and updates the Materialized View (Read DB) optimized for queries.

1. The Write Side (Command)

The system never executes UPDATE orders SET status = 'SHIPPED'. It only ever INSERTS a new OrderShippedEvent to Kafka.

2. The Read Side (Projection)

A separate consumer listens to all events and projects them into a highly optimized database structure (e.g., Elasticsearch for searching, or Redis for fast key-value lookups).

@Service
public class OrderProjectionEngine {
    
    @KafkaListener(topics = "order-events")
    public void updateReadModel(Event event) {
        if (event instanceof OrderCreatedEvent e) {
            readDb.save(new OrderSummary(e.getId(), "PENDING"));
        } else if (event instanceof OrderShippedEvent e) {
            readDb.updateStatus(e.getId(), "SHIPPED");
        }
    }
}
