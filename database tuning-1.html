1.1 PostgreSQL Sandbox: Generating 1,000,000 Realistic Rows

Small tables (100 rows) lie to you—the Cost-Based Optimizer (CBO) will always pick a Sequential Scan because everything fits inside a single 8KB disk page. Run this script in DBeaver to build a high-cardinality dataset in 3 seconds.

Step 1: Create Tables (Intentionally Unindexed First) PostgreSQL DDL

We create a customers table (100k rows) and an orders table (1M rows) with skewed status distributions, JSONB payloads, and timestamps so we can measure real I/O bottlenecks.

-- Drop existing lab tables if re-running
DROP TABLE IF EXISTS lab_orders;
DROP TABLE IF EXISTS lab_customers;

CREATE TABLE lab_customers (
    customer_id BIGSERIAL PRIMARY KEY,
    email VARCHAR(150) NOT NULL,
    region VARCHAR(30) NOT NULL,
    tier VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE lab_orders (
    order_id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_status VARCHAR(20) NOT NULL,
    total_amount NUMERIC(10, 2) NOT NULL,
    order_code VARCHAR(40) NOT NULL,
    metadata JSONB,
    created_at TIMESTAMP NOT NULL
);

Step 2: Seed 100k Customers & 1M Orders via generate_series Fast Bulk Seed

Notice how we engineer data skew: 94% of orders are COMPLETED, 5% are CANCELLED, and only 1% are PENDING. This is critical for testing Partial Indexes later.

-- 1. Insert 100,000 Customers
INSERT INTO lab_customers (email, region, tier, created_at)
SELECT 
    'user_' || g || '@enterprise-lab.io',
    (ARRAY['APAC', 'EMEA', 'NA', 'LATAM'])[1 + (g % 4)],
    CASE WHEN g % 20 = 0 THEN 'VIP' WHEN g % 5 = 0 THEN 'GOLD' ELSE 'STANDARD' END,
    NOW() - (g || ' minutes')::INTERVAL
FROM generate_series(1, 100000) AS g;

-- 2. Insert 1,000,000 Orders with realistic skew
INSERT INTO lab_orders (customer_id, order_status, total_amount, order_code, metadata, created_at)
SELECT 
    1 + (random() * 99999)::BIGINT,
    CASE 
        WHEN g % 100 = 0 THEN 'PENDING'      -- 1% (High selectivity)
        WHEN g % 20 = 0  THEN 'CANCELLED'    -- 5%
        ELSE 'COMPLETED'                     -- 94% (Low selectivity / High skew)
    END,
    ROUND((10 + random() * 990)::NUMERIC, 2),
    'ORD-' || LPAD(g::TEXT, 8, '0'),
    jsonb_build_object('channel', CASE WHEN g % 3 = 0 THEN 'MOBILE' ELSE 'WEB' END, 'priority', g % 5),
    NOW() - ((random() * 525600)::INT || ' minutes')::INTERVAL
FROM generate_series(1, 1000000) AS g;

1.2 MySQL 8.0+ Sandbox Setup & Architectural Differences

How MySQL's InnoDB engine differs physically from PostgreSQL's Heap storage, and how to run the lab on MySQL.

PostgreSQL Heap vs. MySQL InnoDB Clustered Index

  • PostgreSQL (Heap Tuples): Table rows live in an unordered Heap. Every index (even the Primary Key) is a secondary B-Tree pointing to a physical ctid (Page + Tuple slot).
  • MySQL InnoDB (Clustered B-Tree): The table is the Primary Key B-Tree. Leaf nodes of the PK contain the actual row data. Secondary indexes store the Primary Key value, requiring a double B-Tree lookup on cache misses!

MySQL 8+ Recursive CTE Generator

SET SESSION cte_max_recursion_depth = 1000000;

INSERT INTO lab_customers (email, region, tier, created_at)
WITH RECURSIVE seq AS (
    SELECT 1 AS g UNION ALL SELECT g + 1 FROM seq WHERE g < 100000
)
SELECT 
    CONCAT('user_', g, '@enterprise-lab.io'),
    ELT(1 + (g % 4), 'APAC', 'EMEA', 'NA', 'LATAM'),
    IF(g % 20 = 0, 'VIP', 'STANDARD'),
    NOW() - INTERVAL g MINUTE
FROM seq;

1.4 The Optimizer's Brain: Statistics & Buffer Cache Physics

Why running the exact same query twice yields 450ms the first time and 12ms the second time.

Cold Cache vs. Warm Shared Buffers

Never judge an optimization solely by wall-clock milliseconds! The first run pulls 8KB pages from SSD/OS disk cache (Shared Read). The second run reads them directly from RAM (Shared Hit).

The Golden Rule of Weighing Queries: Compare the total number of 8KB Buffers touched (shared hit + read). A query that touches 4 buffers instead of 14,000 buffers will scale under 500 concurrent users, regardless of single-user millisecond jitter.

Inspecting What the Planner Knows

-- Inspect PostgreSQL's internal histogram & cardinality stats
SELECT 
    attname AS column_name,
    n_distinct,
    most_common_vals,
    most_common_freqs
FROM pg_stats
WHERE tablename = 'lab_orders';

2.1 Decoding EXPLAIN (ANALYZE, BUFFERS) Like an Architect

Every number in an execution plan line tells a specific hardware story about CPU cycles, RAM pages, and disk seeks.

Dissecting a Real PostgreSQL Plan Line Line-by-Line Anatomy

EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM lab_orders WHERE customer_id = 4242;

-- OUTPUT:
Seq Scan on lab_orders  (cost=0.00..23845.00 rows=10 width=112) (actual time=0.042..84.310 rows=11 loops=1)
  Filter: (customer_id = 4242)
  Rows Removed by Filter: 999989
  Buffers: shared hit=4520 read=9325
Metric Token Exact Meaning How to Weigh It in Lab
cost=0.00..23845.00 Startup Cost .. Total Cost (Arbitrary planner units, not milliseconds! 1.0 = reading one sequential 8KB page). 0.00 means Seq Scan emits the first row immediately; a Sort node has a high startup cost because it must read all rows before emitting row 1.
rows=10 vs rows=11 Estimated Cardinality vs Actual Rows Returned. If estimated is 10 and actual is 50,000, the planner will mistakenly pick a Nested Loop and stall your server!
loops=1 How many times this specific node was executed. Critical Trap: Multiply actual time and rows by loops! actual time=0.200 ms loops=5000 actually took 1,000 ms (1 full second).
Rows Removed by Filter Rows pulled from storage into CPU memory only to be discarded by the WHERE clause. 999,989 discarded rows for 11 returned rows means 99.99% wasted I/O. Screams for an index!
shared hit=4520 read=9325 8KB Pages from RAM (hit) vs 8KB Pages from Disk/OS (read). (4520 + 9325) * 8KB = ~110.7 MB scanned for a single query. Target under 20 buffers for OLTP point lookups.

2.2 Weighing the 4 Access Paths (Scan Types)

An index is not always faster than a table scan. Understanding when the optimizer switches between these four access paths is key.

Scan Type How It Works Physically When Optimizer Chooses It I/O & Performance Profile
Sequential Scan
(MySQL: type: ALL)		 Streams contiguous 8KB table blocks sequentially from start to finish. Query fetches greater than 15-25% of table rows, or no usable index exists. Fast sequential disk read, but O(N) scaling. Terrible for small point lookups on large tables.
Index Scan
(MySQL: type: ref / range)		 Traverses B-Tree to leaf node, then jumps to the table Heap (random I/O) for every matching row to check MVCC visibility & fetch extra columns. High selectivity (less than 1-2% of rows matching) where non-indexed columns are also selected. O(log N) lookup. Awesome for 1–500 rows; degrades rapidly if thousands of random heap jumps occur.
Bitmap Index Scan + Bitmap Heap Scan Step 1: Scans B-Tree and builds an in-memory bitmask of matching 8KB page numbers.
Step 2: Sorts page numbers sequentially and reads each heap page once!		 Medium selectivity (1% to 15% of rows), or combining two separate indexes via BitmapAnd / BitmapOr. Eliminates random I/O thrashing! Bridges the gap between Index Scan and Seq Scan.
Index-Only Scan
(MySQL: Using index)		 Answers the entire query straight from the B-Tree leaf nodes. Zero Heap table access (if Visibility Map confirms pages are all-visible). All columns in SELECT, WHERE, and ORDER BY exist inside the index definition (or INCLUDE clause). The fastest possible read in RDBMS. Often requires only 3–4 buffer hits total.

2.3 Weighing the 3 Physical Join Algorithms

When joining lab_customers and lab_orders, the database engine picks one of three physical algorithms.

1. Nested Loop Join Best for Small Outer Rows

For each row in the outer table, look up matching rows in the inner table (ideally via an Index).

for (Customer c : outerRows) { // e.g. 5 VIP customers indexLookupOrders(c.id); // 5 fast B-Tree lookups }

Complexity: O(N * log M) with inner index, or catastrophic O(N * M) without inner index.

2. Hash Join Best for Large Unsorted Sets

Loads the smaller table into an in-memory Hash Table (inside work_mem), then streams the larger table once, probing the hash map in O(1) time.

1. Hash Node: Build HashMap from lab_customers (Batches: 1) 2. Probe: Stream lab_orders & match hash(customer_id)

Red Flag: Check Batches: 1 in EXPLAIN. If Batches > 1, the hash table spilled to disk temp files!

3. Merge Join Best for Pre-Sorted / Indexed Streams

Requires both inputs to be sorted on the join key. Advances two pointers in lockstep like a zipper. Extremely fast if both sides are already sorted via B-Tree indexes, and never runs out of memory for huge datasets.

3.1 SARGability (Search Argument Able Queries)

The #1 reason production indexes are silently ignored: wrapping an indexed column inside a function, math expression, or implicit type cast.

❌ DON'T: Non-SARGable (Index Blindness) Seq Scan: 95ms

Because the B-Tree stores raw created_at timestamps, wrapping the column in EXTRACT() or DATE() forces PostgreSQL to evaluate the function on all 1,000,000 rows before comparing.

CREATE INDEX idx_orders_created ON lab_orders(created_at);

-- BAD: Function on left side of operator breaks B-Tree traversal!
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_orders 
WHERE EXTRACT(YEAR FROM created_at) = 2026;

✅ DO: SARGable Range Predicate Index Scan: 0.4ms

Always isolate the raw indexed column on one side of the comparison operator and push the math/functions to the constant parameter side.

-- GOOD: Direct B-Tree range seek from start bound to end bound
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_orders 
WHERE created_at >= '2026-01-01 00:00:00' 
  AND created_at <  '2027-01-01 00:00:00';

3.2 Composite Column Ordering (ESR Rule) & Covering Indexes

When creating a multi-column index (A, B, C), column order determines whether the B-Tree can filter and sort simultaneously.

The ESR Rule: Equality ➔ Sort ➔ Range Architecture Rule

A B-Tree is sorted first by Column 1, then ties are broken by Column 2. The moment you apply a Range filter (>, <, BETWEEN) on a column, the B-Tree ordering is broken for any subsequent columns in that index!

❌ Wrong Order: (created_at, customer_id)

-- Range first, Equality second:
-- Cannot seek directly to customer_id = 500!
CREATE INDEX idx_bad ON lab_orders (created_at, customer_id);

SELECT * FROM lab_orders
WHERE customer_id = 500 
  AND created_at > NOW() - INTERVAL '30 days';

✅ Optimal Order + Covering INCLUDE

-- 1. Equality (customer_id)
-- 2. Range/Sort (created_at)
-- 3. Payload (INCLUDE total_amount for Index-Only Scan!)
CREATE INDEX idx_orders_cust_date_cov 
ON lab_orders (customer_id, created_at DESC) 
INCLUDE (total_amount);

EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, created_at, total_amount
FROM lab_orders
WHERE customer_id = 500 
  AND created_at > NOW() - INTERVAL '30 days';

3.3 Partial Indexes: Conquering Data Skew with 99% Less RAM

Why index 940,000 COMPLETED orders that your active worker queue never queries?

Full Index on Skewed Column

CREATE INDEX idx_full_status ON lab_orders(order_status);
-- Index Size on Disk: ~21 MB (Indexes all 1,000,000 rows)

Every single INSERT or status UPDATE pays the write amplification penalty of maintaining this 21 MB B-Tree.

Partial Index (Filtered B-Tree) PostgreSQL Superpower

CREATE INDEX idx_partial_pending_orders 
ON lab_orders (created_at) 
WHERE order_status = 'PENDING';
-- Index Size on Disk: ~240 KB (99% smaller! Fits in L2 CPU Cache)

Queries filtering on WHERE order_status = 'PENDING' ORDER BY created_at execute in 0.05ms with virtually zero write overhead on completed orders.

3.4 Deep Pagination: Why OFFSET 500000 Kills Databases

OFFSET does not skip rows on disk—it forces the database to fetch, materialize, and sort 500,020 rows just to throw the first 500,000 in the trash.

❌ DON'T: Offset Pagination O(N) Degradation

EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, order_code, created_at
FROM lab_orders
ORDER BY order_id ASC
LIMIT 20 OFFSET 500000;
-- Execution Time: ~145 ms | Buffers Touched: 6,200+

✅ DO: Keyset / Seek Pagination O(log N) Constant 0.04ms

-- Pass the last seen order_id from the previous page cursor:
EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, order_code, created_at
FROM lab_orders
WHERE order_id > 500000
ORDER BY order_id ASC
LIMIT 20;
-- Execution Time: ~0.04 ms | Buffers Touched: 4

3.5 The 7 Deadly SQL Anti-Patterns Checklist

A quick diagnostic reference for code reviews and production troubleshooting.

# Anti-Pattern (The "Don't") Why It Destroys Performance The Architect's Fix
1 SELECT * on wide tables with JSONB/TEXT Prevents Index-Only Scans, triggers PostgreSQL TOAST table decompression, and saturates network buffers. Project strictly required columns so Covering Indexes can satisfy the query.
2 NOT IN (SELECT nullable_col FROM ...) If a single NULL exists in the subquery, SQL three-valued logic evaluates the entire predicate to UNKNOWN (returns 0 rows). Use NOT EXISTS (SELECT 1 FROM ... WHERE ...) which uses a fast Hash Anti-Join and handles NULLs safely.
3 OR conditions across two different columns WHERE customer_id = 10 OR order_code = 'X' cannot traverse a single B-Tree; forces either a Seq Scan or two separate scans merged via BitmapOr. Ensure both columns have individual indexes so BitmapOr works, or rewrite as UNION ALL.
4 Implicit Type Conversion (e.g., WHERE varchar_col = 12345) Passing an integer to a VARCHAR column forces the engine to cast every row in the table to a number, disabling the B-Tree index. Match Java/JDBC parameter types strictly to SQL column types ('12345').
5 Unindexed Foreign Keys PostgreSQL automatically indexes Primary Keys, NOT Foreign Keys. Deleting a parent row in lab_customers triggers a Full Table Scan on lab_orders! Always create an explicit B-Tree index on every Foreign Key column.
6 Sorting huge datasets without checking Sort Method If an ORDER BY exceeds work_mem (default 4MB in PG), it switches from quicksort (Memory) to external merge Disk. Provide an index matching the ORDER BY clause or increase session work_mem for reporting queries.
7 Over-Indexing Write-Heavy Tables Having 12 indexes on an OLTP table turns 1 logical INSERT into 13 physical page modifications and blocks PostgreSQL HOT updates. Drop unused indexes via pg_stat_user_indexes (idx_scan = 0).

Task: Weigh the cost of the OFFSET 100000 scan. Refactor the pagination to Keyset/Seek pagination (WHERE o.order_id > 100000) and observe the dramatic drop in execution time and buffers.

Challenge 9: JSONB GIN Indexing (@>) vs. ->> Text Extraction HARD

Your microservices store semi-structured channel and priority attributes inside the metadata JSONB column. Developers write queries using ->> text extraction, causing 1,000,000-row Sequential Scans.

-- Developer's slow query:
EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, total_amount 
FROM lab_orders 
WHERE metadata->>'channel' = 'MOBILE' 
  AND (metadata->>'priority')::INT = 4;

Task: Create a Generalized Inverted Index (GIN) using jsonb_path_ops on metadata and rewrite the WHERE clause to use the JSONB containment operator (@>) so PostgreSQL executes a fast Bitmap Index Scan.

🔍 Lab Guidance & DBeaver Steps

  • Standard B-Tree indexes don't automatically index every key inside a JSONB document.
  • Create a GIN index: CREATE INDEX idx_orders_meta_gin ON lab_orders USING GIN (metadata jsonb_path_ops);
  • Rewrite the filter using containment: WHERE metadata @> '{"channel": "MOBILE", "priority": 4}'::jsonb.

🏆 Architectural Solution & Before/After Metrics

CREATE INDEX idx_orders_meta_gin 
ON lab_orders USING GIN (metadata jsonb_path_ops);

EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, total_amount 
FROM lab_orders 
WHERE metadata @> '{"channel": "MOBILE", "priority": 4}'::jsonb;

Verdict: Switches from a parallel Seq Scan parsing JSON on 1M rows (~160ms) to a Bitmap Index Scan on idx_orders_meta_gin (~8ms).
