1. High-Scale Signup Architecture: Bloom Filters & Transactional Outbox

Shielding the primary relational database from read storms while guaranteeing zero-downtime capacity migrations and atomic state propagation.

The Probabilistic Guardrail Fast Path

A Bloom filter does not solve race conditions directly; rather, it acts as a shock absorber in front of PostgreSQL. By hashing a candidate username through k functions (simulated via MurmurHash3 128-bit splitting: h_i = h_1 + i * h_2 (mod m)), it answers membership queries in O(k) memory time.

  • Definitely Does Not Exist (Bit = 0): If even a single hashed bit index is 0, the username has never been claimed. Approve immediately with zero database hits.
  • May Exist / False Positive (All Bits = 1): Either the username is taken, or overlapping hashes from other users flipped those bits. Fall back to a primary database query to verify.
  • The Final Race Arbiter: The PostgreSQL UNIQUE constraint handles concurrent millisecond collisions via ACID serialization.
[User Request: "soham"] │ ▼ [Murmur3_128 Hash] ──► Indices [2, 7, 11] │ ├─► Any bit == 0? ──► [100% Available! Skip DB] │ └─► All bits == 1? ─► [Collision / Taken] ──► Query PostgreSQL

Solving Dual-Write via Transactional Outbox Eventual Sync

Updating the Bloom filter before the DB commit risks "poisoning" the bit array if the DB transaction rolls back. Updating it directly after the DB commit risks losing the update if the JVM crashes between the PostgreSQL commit and the Redis network call.

@Service
public class UserRegistrationService {
    @Transactional
    public void registerUser(String username) {
        // 1. Primary table insert (Enforces UNIQUE constraint)
        userRepository.save(new AppUser(username));

        // 2. Outbox insert in the SAME physical ACID transaction
        outboxRepository.save(new OutboxEvent("USER_CREATED", username));
    }
}
Capacity Sizing (tryInit(10_000_000, 0.01)): You tell Redisson the expected total insertions (n) and acceptable false-positive probability (p = 1%) so it calculates the fixed bit array length (m) and hash count (k).

Zero-Downtime Bloom Filter Scaling (V1 to V2 Migration) Blue-Green Hydration

Because modulo arithmetic depends on a fixed array size m, a Bloom filter cannot be dynamically resized. When capacity approaches limits, execute a 4-phase live migration using Spring Batch Chunking and a Dual-Write / Short-Circuit Abstraction.

1. Memory-Safe Hydration (Spring Batch)

@Bean
public ItemReader<String> usernameReader(DataSource ds) {
    return new JdbcPagingItemReaderBuilder<String>()
        .name("usernameReader").dataSource(ds)
        .selectClause("SELECT username").fromClause("FROM users")
        .sortKeys(Map.of("id", Order.ASCENDING))
        .rowMapper((rs, rowNum) -> rs.getString("username"))
        .pageSize(10_000) // Stream 10k rows at a time; prevents OOM
        .build();
}

2. Short-Circuit Migration Proxy

@Override
public boolean mightContain(String username) {
    if (cutoverComplete) return v2.mightContain(username);
    if (!v2HydrationComplete) return v1.mightContain(username);

    // Hydration done: Use larger V2 to short-circuit V1 false positives!
    if (!v2.mightContain(username)) return false;
    return v1.mightContain(username);
}

@Override
public void add(String username) {
    if (!cutoverComplete) v1.add(username);
    v2.add(username); // Idempotent dual-write during migration
}

2. Demystifying Spring / Jakarta @Transactional Mechanics

Understanding AOP proxy boundaries, EJB philosophical roots, autonomous propagation, state versioning, and self-healing retry loops.

Lab 1 & 2: The EJB Legacy & Exception Philosophy The Default Trap

Spring inherited its rollback rules from EJB: Unchecked exceptions (RuntimeException, Error) signal fatal infrastructure or programming defects, triggering an automatic rollback. Checked exceptions (Exception) were historically viewed as recoverable "alternative return values," causing the proxy to commit partial work by default.

Modern Domain Standard: All domain exceptions (e.g., InsufficientFundsException) MUST extend RuntimeException. This guarantees fail-safe automatic rollbacks, keeps method signatures clean, and works seamlessly with Java Streams/Lambdas. 
// Explicitly overriding proxy rules for legacy SDKs & side-effects
@Transactional(
    rollbackFor = LegacyPaymentCheckedException.class,
    noRollbackFor = NotificationDeliveryRuntimeException.class
)
public void processOrder(Order order) throws LegacyPaymentCheckedException {
    orderRepository.save(order);
    legacyGateway.charge(); // Throws checked -> Rolls back!
    notificationClient.sendSms(); // Throws runtime -> Commits anyway!
}

Lab 3: Autonomous Auditing vs. State Time-Travel Audit Architecture

A rollback shreds everything inside its physical transaction boundary. To audit failed attempts versus successful state transitions, combine two complementary tools:

  • Business Intent / Failure Logging (Propagation.REQUIRES_NEW): Suspends the outer transaction, borrows a second physical connection from HikariCP, commits the audit log independently, and resumes the outer transaction.
  • Temporal State Versioning (Hibernate Envers @Audited): Piggybacks on the same transaction to record snapshots in orders_aud and revinfo (REVTYPE: 0=ADD, 1=MOD, 2=DEL). Blind to rollbacks, but effortless for compliance history.
@Service
public class AuditLogService {
    // Must reside in a separate Spring Bean to avoid self-invocation bypass!
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAttempt(String action, String detail) {
        auditRepo.save(new AuditLog(action, detail));
    }
}
The HikariCP Exhaustion Trap: Every nested REQUIRES_NEW call holds 2 simultaneous DB connections per thread. Under high concurrency, this can deadlock your connection pool if overused.

Lab 4: Transient Resilience with @Retryable Self-Healing

When wrapping @Transactional with @Retryable, the Retry AOP interceptor sits outside the Transaction interceptor. If a transient lock exception occurs, the inner transaction rolls back cleanly, waits for the backoff period, and initiates a brand-new database transaction on the next attempt.

@Retryable(
    retryFor = { CannotAcquireLockException.class, OptimisticLockingFailureException.class },
    maxAttempts = 3,
    backoff = @Backoff(delay = 1000, multiplier = 2.0)
)
@Transactional
public void processContendedOrder(String product) {
    // Executed in a fresh transaction on each retry attempt
    orderRepository.save(new AppOrder(product, "CONFIRMED"));
}

@Recover
public void recoverOrder(Exception e, String product) {
    // Triggered after all 3 attempts fail. Route to Dead Letter Queue (DLQ).
    dlqPublisher.publishFailedOrder(product, e.getMessage());
}

3. Database Locking Architecture & Concurrency Control

Bridging JPA annotations to physical PostgreSQL row locks, wait policies, and lock-free multi-JVM optimistic concurrency.

JPA Locking Annotations & Hint Directives Reference

Annotation / Hint Attribute / Value Generated SQL Equivalent Engine Behavior & Architectural Purpose
@Lock LockModeType.PESSIMISTIC_WRITE SELECT ... FOR UPDATE Acquires an exclusive row lock. Blocks all other concurrent writers and locking readers until transaction commits/rolls back.
@Lock LockModeType.PESSIMISTIC_READ SELECT ... FOR SHARE Acquires a shared lock. Other transactions can read the row, but no transaction can modify or exclusively lock it.
@Lock / @Version LockModeType.OPTIMISTIC UPDATE ... WHERE id=? AND version=? No database lock held during read. Detects concurrent modifications atomically at flush time via row update counts.
@QueryHint lock.timeout = "0" SELECT ... FOR UPDATE NOWAIT Fail-Fast: Prevents thread pool blocking. Throws PessimisticLockingFailureException immediately if row is locked.
@QueryHint lock.timeout = "-2" SELECT ... FOR UPDATE SKIP LOCKED Worker Queue: Silently ignores locked rows during index scan and locks the next available unlocked row.
@QueryHint lock.timeout = "3000" SET LOCAL lock_timeout = 3000 Bounded Wait: Blocks the thread up to 3,000ms waiting for the lock before aborting with an exception.

1. Pessimistic Write + NOWAIT High Contention

Ideal for financial ledger transfers or inventory deduction where collisions are frequent and data integrity is paramount. Using timeout = "0" protects HikariCP threads from hanging indefinitely.

public interface AccountRepo extends JpaRepository<Account, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints({
        @QueryHint(
            name = "jakarta.persistence.lock.timeout", 
            value = "0" // NOWAIT
        )
    })
    Optional<Account> findByIdForUpdate(Long id);
}

2. Pessimistic SKIP LOCKED Distributed Queue

Turns PostgreSQL into a high-speed concurrent job broker. When 50 Spring Boot pods poll the outbox table simultaneously, PostgreSQL skips locked rows in the index scan and hands each pod a distinct batch.

public interface OutboxRepo extends JpaRepository<OutboxEvent, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints({
        @QueryHint(
            name = "jakarta.persistence.lock.timeout", 
            value = "-2" // SKIP LOCKED
        )
    })
    @Query("SELECT e FROM OutboxEvent e WHERE e.processed = false")
    List<OutboxEvent> pollBatch(Pageable pageable);
}

Works across independent JVMs and Kubernetes pods without Redis locks because the arbitration happens atomically inside the database's SQL execution engine.

public class Wallet {

4. Distributed Consistency Spectrum & Spring Boot Implementations

Architecting how Strong, Eventual, Causal, and Session consistency models cooperate across microservices.

Architectural Cooperation Matrix: How Consistency Models Work Together

Consistency Model Role in the System Architecture Primary Pros Primary Cons Real-World Use Cases
Strong (ACID / Linearizable) The Command Core: Acts as the single source of truth for state mutations, then emits events downstream. Zero dirty/stale reads; strict mathematical correctness; simple mental model. High latency due to lock serialization; reduced availability under partitions (CAP). Core banking ledgers, billing, inventory allocation, seat booking.
Eventual (BASE / Async) The Query Scale Layer: Consumes events from the Strong core via Kafka/Outbox to hydrate read replicas. Massive horizontal read throughput; zero read locking; survives primary DB outages. Replication lag causes temporary stale reads; requires idempotent consumers. YouTube view counters, product catalogs, analytics dashboards, search indexes.
Causal (Dependency-Ordered) The Logical Sequencer: Sits on edge consumers; enforces cause-and-effect ordering before exposing Eventual data. Prevents nonsensical out-of-order UI states without paying the cost of global locking. Requires vector clocks or parent-ID dependency checks in message consumers. Comment threads, WhatsApp/Slack replies, collaborative document editing.
Session (Read-Your-Writes) The UX Router: Pins the mutating user to the Strong primary node briefly while everyone else reads Eventual replicas. Gives the active user instant feedback while preserving 99% replica offloading. Requires sticky tokens/headers and custom AbstractRoutingDataSource logic. Updating user profile bio/avatar, e-commerce order confirmation screens.

1. Eventual Consistency (CQRS Command/Query Split)

Decouples high-velocity writes from read projections using an append-only log and asynchronous Kafka consumers.

// COMMAND SIDE: Fast write + Event emission
@Transactional
public void recordVideoView(Long videoId) {
    viewLogRepo.save(new ViewLog(videoId, Instant.now()));
    kafkaTemplate.send("video-views", videoId.toString());
}

// QUERY SIDE: Eventual projection update
@KafkaListener(topics = "video-views")
@Transactional
public void projectViewCount(String videoId) {
    videoStatsReadRepo.incrementCount(Long.valueOf(videoId));
}

2. Causal Consistency (Parent-Child Guard)

Ensures an effect (Reply B) is never committed to a local read store before its cause (Question A) has arrived over the network.

@KafkaListener(topics = "chat-events")
public void consumeChatMessage(ChatMessage msg) {
    // Verify causal parent exists in local replica before committing
    if (msg.getParentId() != null && !chatRepo.existsById(msg.getParentId())) {
        // Trigger Kafka retry / backoff until parent message arrives
        throw new CausalParentMissingException("Awaiting parent: " + msg.getParentId());
    }
    chatRepo.save(msg);
}

3. Session Consistency (Read-Your-Own-Writes via Spring AbstractRoutingDataSource)

Routes a user's immediate post-mutation GET requests to the Primary PostgreSQL node while offloading standard traffic to Read Replicas.

Context Holder & Dynamic DataSource Router

public class DbRouteContext {
    private static final ThreadLocal<String> ROUTE = new ThreadLocal<>();
    public static void set(String db) { ROUTE.set(db); }
    public static String get() { return ROUTE.get(); }
    public static void clear() { ROUTE.remove(); }
}

public class PrimaryReplicaRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return DbRouteContext.get() != null ? DbRouteContext.get() : "REPLICA";
    }
}

Servlet Filter Inspecting Mutation State

@Component
public class SessionConsistencyFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        try {
            // Pin to PRIMARY if mutating or carrying a recent-write session token
            boolean isMutationOrRecent = !req.getMethod().equals("GET") 
                                         || req.getHeader("X-Recent-Write-Token") != null;
            DbRouteContext.set(isMutationOrRecent ? "PRIMARY" : "REPLICA");
            chain.doFilter(req, res);
        } finally {
            DbRouteContext.clear(); // Crucial for Virtual/Platform thread reuse
        }
    }
}
