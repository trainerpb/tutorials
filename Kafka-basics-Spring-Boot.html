Event-Driven Architecture: Kafka & Spring Boot

Core Concepts (The "Why")

Kafka is not a traditional message queue (like RabbitMQ). It is a distributed, append-only commit log. Messages are written to disk, replicated, and retained for a configured period, allowing multiple distinct consumer groups to read the same data at their own pace.

  • Broker: A single Kafka server node. A cluster consists of multiple brokers.
  • Topic: A logical category or feed name to which records are published.
  • Partition: The physical unit of scale. A topic is split into partitions distributed across brokers. Ordering is guaranteed only within a single partition.
  • Producer: The application publishing events. It uses a "Routing Key" to hash messages to a specific partition.
  • Consumer Group: A logical group of consumer instances scaling the read workload. Kafka guarantees that a specific partition is assigned to exactly one consumer within a group.

Spring Boot 3 Integration

Spring Kafka abstracts away the boilerplate of the native Java client. To prevent message loss and achieve At-Least-Once delivery, you must set enable.auto.commit=false and use AckMode.MANUAL_IMMEDIATE so the consumer only acknowledges the message after successful processing[cite: 2].

1. application.yml

spring:
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: analytics-group
      auto-offset-reset: earliest
      enable-auto-commit: false # Crucial for At-Least-Once
    listener:
      ack-mode: manual_immediate # We control the commit
      concurrency: 3 # Match listener concurrency to partitions for scale

2. The Producer

@Service
public class EventProducer {
    private final KafkaTemplate<String, String> kafkaTemplate;

    public EventProducer(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void sendBusinessEvent(String entityId, String payload) {
        // Using entityId as the key guarantees ordered partitions
        kafkaTemplate.send("business-events", entityId, payload);
    }
}

3. The Consumer (Manual Acknowledgment)

@Service
public class EventConsumer {

    @KafkaListener(topics = "business-events")
    public void processEvent(ConsumerRecord<String, String> record, Acknowledgment ack) {
        try {
            System.out.println("Processing key: " + record.key());
            // Execute business logic here...
            
            // Only acknowledge if logic succeeds
            ack.acknowledge(); 
        } catch (Exception e) {
            // Handle or throw. Throwing blocks the partition without a Retry config.
            throw new RuntimeException("Processing failed");
        }
    }
}

Advanced Resiliency & Exactly-Once Semantics

In production, network partitions, transient database timeouts, and application crashes are inevitable. A pro-level architecture anticipates this without blocking message pipelines.

1. Non-Blocking Retries & Dead Letter Queues (DLQ)

By default, if a consumer throws an exception, Spring blocks the partition and retries locally. This creates a bottleneck. For non-blocking retries, use the @RetryableTopic annotation. It automatically creates backoff topics and forwards the message to a DLT (Dead Letter Topic) if all attempts fail[cite: 2]. Fatal exceptions bypass retries and route directly to the DLT[cite: 2].

@RetryableTopic(
    attempts = "3",
    backoff = @Backoff(delay = 2000, multiplier = 2.0),
    dltStrategy = DltStrategy.FAIL_ON_ERROR,
    exclude = { IllegalArgumentException.class } // Fatal errors skip to DLT
)
@KafkaListener(topics = "orders", groupId = "order-group")
public void processOrder(OrderEvent event) {
    // Transient DB failures will be routed to orders-retry-0, orders-retry-1...
}

2. Exactly-Once Processing (Idempotency)

Kafka guarantees "Exactly-Once Processing" by coordinating the Producer, the Broker, and the Consumer[cite: 2]. Even with Kafka transactions, your application must defend against duplicates. Implement Idempotent Consumers by checking unique business keys against a database constraint to discard safely any duplicate side effects[cite: 2].

3. Consumer Rebalancing & Sticky Assignors

When a consumer instance crashes or scales up, the Consumer Group Coordinator triggers a Rebalance. Historically, this meant a "Stop The World" event where all consumers paused and dropped partitions. To fix this, modern Kafka uses the Cooperative Sticky Assignor, which allows consumers to keep their existing partitions while only reassigning the partitions of the dead node, severely reducing downtime.
