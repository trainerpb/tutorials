Module 1: Google Cloud Foundations & The "Always Free" Architecture

Understanding OpEx Billing, Service Boundaries, and Zero-Cost Guardrails for Spring Boot Architects

CapEx vs OpEx IaaS vs PaaS Billing Guardrails

1. The Cloud Economic Shift & Deployment Models

Cloud computing shifts IT infrastructure from upfront Capital Expenditure (CapEx) (buying physical servers) to Operational Expenditure (OpEx) (pay-as-you-go metered billing). As a Java Spring Boot architect, you primarily select between two core NIST service models on GCP:

🖥️ Infrastructure as a Service (IaaS) — Compute Engine

Provides virtualized hardware slices (VMs, persistent disks, VPC networks). Google manages the physical data center and KVM hypervisor; you manage the Linux OS, JDK installation, firewall ports, and Spring Boot JAR execution.

🚀 Platform as a Service (PaaS) — Cloud Run / App Engine

Provides a managed execution environment for containerized applications (OCI images built via Jib or Docker). It scales to zero when idle and abstracts away all OS patching and server maintenance.

2. The 2026 Google Cloud "Always Free" Resource Boundaries

Google Cloud offers two parallel incentives: a 90-Day / $300 Free Trial and an ongoing Always Free Tier. Staying strictly within the boundaries below ensures a $0.00 monthly invoice indefinitely:

GCP Service Always Free Allocation Critical Configuration Rules Spring Boot Architecture Use Case
Compute Engine (IaaS) 1 non-preemptible e2-micro instance per month Must be in us-central1 (Iowa), us-east1 (S. Carolina), or us-west1 (Oregon). Hosting an always-on monolithic Spring Boot JAR, Nginx reverse proxy, or lightweight service.
Persistent Disk 30 GB-months of Standard Persistent Disk Must select pd-standard (HDD). Default pd-balanced (SSD) costs ~$1.00/10GB! Boot disk for your Linux OS, JVM binaries, and application log files.
Cloud Run (PaaS) 2 million requests, 360,000 GB-sec memory, 180,000 vCPU-sec Set max instances to 1–2 and allocate CPU only during request processing. Stateless Spring Boot microservices packaged via Google Jib or Docker.
Cloud Storage (GCS) 5 GB-months of Standard Storage + 5,000 Class A Ops Must be provisioned in US regions (us-central1, us-east1, us-west1). Storing static web assets, user file uploads, and compiled .jar artifacts.
Artifact Registry 0.5 GB storage per month Periodically prune old container tags to remain under 500 MB. Hosting private Docker/OCI container images for Spring Boot deployments.
Firestore (NoSQL) 1 GB storage, 50k reads, 20k writes/day Native mode database; zero maintenance required. Storing user sessions, application state, and document-oriented entities.
Why does the Console UI show a "$7.11/month" estimate for an e2-micro VM?
1. The $6.11 Compute Estimate: The GCP Console UI always displays the raw retail price of the e2-micro VM ($6.11). It does not dynamically subtract the Always Free discount on the creation form. Instead, Google automatically applies a 100% credit at the end of the billing cycle if the VM is in an eligible US region.
2. The $1.00 Disk Estimate: By default, GCP selects a 10 GB Balanced Persistent Disk (SSD), which is not free. Changing the Boot Disk type to Standard Persistent Disk (HDD) (up to 30 GB) eliminates this $1.00 charge completely.

3. Billing Safety Guardrails & Account Protection

🛡️ Will My Credit Card Be Auto-Charged?

No. While on the Free Trial, Google Cloud will never automatically bill your credit card if your $300 credit expires or the 90 days end. Your instances will simply pause until you manually click "Upgrade to a Paid Account".

🔔 Setting a $0.00 Budget Alert

Always navigate to Billing → Budgets & alerts immediately upon creating an account. Set a target budget of $0.00 (or $1.00) with email alerts at 50%, 90%, and 100% thresholds to catch accidental paid resources early.

Module 2: Google Compute Engine (VMs) & Cloud Storage Buckets

Provisioning Linux Virtual Machines, Configuring VPC Firewalls, Serving Apps, and Managing Object Storage

Compute Engine VPC Firewall Rules Cloud Storage (GCS)

1. Anatomy of a Compute Engine Virtual Machine

⚙️ Machine Type (e2-micro)

Provides 2 shared vCPUs and 1 GB of RAM. Ideal for lightweight Spring Boot APIs, Nginx servers, and learning Linux administration.

🌐 Internal vs External IPs

Internal IP: Private RFC 1918 address for VPC-internal communication.
External IP: Public internet routable address to access your web apps from a browser.

🛑 VM Lifecycle Billing

Stopped (Terminated): $0 compute charges, but attached disks and static IPs still bill.
Deleted: Destroys both VM and boot disk, halting 100% of billing.

2. Running Web Applications on Your VM (Python, Nginx & Java)

After clicking the SSH button in the GCP Console to launch the browser-based Linux terminal, you can immediately serve web traffic on Port 80 (or custom ports like 8080):

Option A: Instant Python 3 HTTP Server (Port 80)

BASH — VM SSH TERMINAL 
# 1. Create a simple HTML test payload
echo "<h1>Hello from my Google Cloud VM!</h1><p>App is live.</p>" > index.html

# 2. Bind Python's built-in server to privileged Port 80 (Press Ctrl+C to stop)
sudo python3 -m http.server 80

Option B: No-Python Alternatives (Nginx, Java 18+ jwebserver, BusyBox)

BASH — JAVA & LINUX NATIVE SERVERS 
# Alternative 1: Install & Serve via Nginx (Production Daemon)
sudo apt update && sudo apt install -y nginx
sudo mv index.html /var/www/html/index.html

# Alternative 2: Use Java's Built-in Simple Web Server (JDK 18+)
sudo apt install -y default-jdk
sudo jwebserver -p 80 -b 0.0.0.0

# Alternative 3: Linux Native BusyBox HTTPD
sudo busybox httpd -f -p 80

Option C: Deploying a Spring Boot Executable JAR in the Background

BASH — SPRING BOOT BACKGROUND EXECUTION 
# Run Spring Boot JAR detached from terminal using nohup so it survives SSH exit
nohup java -jar my-spring-app-0.0.1-SNAPSHOT.jar > app.log 2>&1 &

# Stream live Tomcat startup logs
tail -f app.log

3. Opening Custom Ports via VPC Firewall Rules (e.g., Port 8080)

By default, GCP blocks all incoming (Ingress) traffic from the public internet unless explicitly permitted. Checking "Allow HTTP traffic" only opens Port 80. For Spring Boot (Port 8080), you must add a VPC Firewall Rule:

  1. In the GCP Console search bar, navigate to VPC network → Firewall and click Create Firewall Rule.
  2. Name: allow-spring-8080 | Direction: Ingress | Action on match: Allow.
  3. Targets: Choose All instances in the network (or use Specified target tags like spring-app).
  4. Source IPv4 ranges: 0.0.0.0/0 (allows public access from any IP address).
  5. Protocols and ports: Check TCP and enter 8080. Click Create.

4. Google Cloud Storage (GCS) Buckets

Cloud Storage is a globally accessible, flat-namespace Object Storage system (analogous to AWS S3). Unlike a persistent boot disk (Block Storage), you store discrete immutable files (objects) inside globally unique buckets:

Storage Class Target Access Frequency Typical Enterprise Use Case
Standard Hot data accessed frequently Active website assets, application uploads, compiled Spring Boot JAR staging.
Nearline < Once every 30 days Monthly application backups and user-generated archive media.
Coldline < Once every 90 days Quarterly disaster recovery snapshots and rarely read telemetry logs.
Archive < Once every 365 days Long-term regulatory compliance, banking audits, and medical record retention.

1. Web Cloud Shell vs. Local gcloud CLI Installation

🌐 Google Cloud Shell (Web Browser)

  • Free, ephemeral Debian Linux VM launched from the top-right >_ icon in the GCP Console.
  • Pre-installed with gcloud, Java, Docker, and Terraform; pre-authenticated to your account.
  • Limitation: Times out after inactivity; cannot directly access files on your local laptop without manual upload.

💻 Local gcloud CLI (Industry Standard)

  • Installed directly on your Windows/Mac/Linux workstation (just like the AWS CLI).
  • Essential for local IDE integration (IntelliJ IDEA, VS Code), local Maven/Gradle builds, and pushing artifacts directly from your hard drive.

3. Advanced Output Formatting (--format & --filter)

Instead of parsing text with awk or grep, gcloud provides built-in projection and filtering flags ideal for automation scripts:

BASH — CUSTOM TABLES, JSON, YAML & VALUE EXTRACTION 
# 1. Extract ONLY the raw External IP of a VM (for scripts)
gcloud compute instances describe instance-20261019-063356 \
    --format="get(networkInterfaces[0].accessConfigs[0].natIP)"

# 2. Render a custom clean table showing Name, Machine Type, and Status
gcloud compute instances list \
    --format="table(name, machineType.basename(), status, networkInterfaces[0].accessConfigs[0].natIP:label=EXTERNAL_IP)"

# 3. Filter only RUNNING or TERMINATED instances
gcloud compute instances list --filter="status=RUNNING"
gcloud compute instances list --filter="status:TERMINATED"

# 4. Export full VM metadata as JSON or YAML
gcloud compute instances describe instance-20261019-063356 --format=json

Module 4: Infrastructure as Code (IaC) with HashiCorp Terraform

Cloud Composability, Declarative Provisioning, ADC Authentication, State Files, and Plan Blueprints

1. Why Terraform? Imperative CLI vs. Declarative IaC

In cloud architecture, Composability is the practice of treating compute, storage, and networking as modular building blocks assembled on demand. While gcloud CLI is Imperative (you specify exact step-by-step commands), Terraform is Declarative (you declare the desired target architecture in .tf files, and Terraform calculates the necessary API calls).

🔌 Multi-Cloud Provider Resolution

Even if you have gcloud, aws, and az CLIs installed on the same machine, Terraform knows which cloud to use based on the provider "google" block in your code.

🔑 The ADC Authentication Bridge

Terraform does not read standard interactive gcloud auth login sessions. You must run gcloud auth application-default login once so Terraform can load the local ADC JSON token.

☕ Do Java Architects Memorize HCL?

No! You can use CDK for Terraform (CDKTF) to write infrastructure in pure Java, use terraform plan -generate-config-out, or use IntelliJ HCL autocomplete.

CMD — STEP 1: GENERATE APPLICATION DEFAULT CREDENTIALS (ADC) 
# Run this in Windows Command Prompt to fix "Error: Attempted to load application default credentials..."
# Saves token to: C:\Users\<User>\AppData\Roaming\gcloud\application_default_credentials.json
gcloud auth application-default login

2. Complete Free-Tier GCP Configuration (main.tf)

Terraform automatically merges all .tf files in your working folder. While you can name a file my-first-tf-vm.tf, standard enterprise conventions separate code into main.tf, variables.tf, outputs.tf, and providers.tf. (Note: On Windows, verify Notepad didn't save your file as main.tf.txt, or Terraform will say "No changes"!)

HCL — main.tf (VM + FIREWALL + CLOUD STORAGE BUCKET) 
# 1. Configure the Google Cloud Provider
provider "google" {
  project = "ivory-link-511508-u3"
  region  = "us-central1"
  zone    = "us-central1-a"
}

# 2. Provision Always-Free e2-micro VM with 30GB Standard Disk
resource "google_compute_instance" "tf_vm" {
  name         = "my-first-tf-vm"
  machine_type = "e2-micro"

  boot_disk {
    initialize_params {
      image = "debian-cloud/debian-12"
      type  = "pd-standard"
      size  = 30
    }
  }

  network_interface {
    network = "default"
    access_config {} # Assigns ephemeral Public External IP
  }

  tags = ["spring-app", "http-server"]
}

# 3. Provision VPC Firewall Rule for Spring Boot (8080) & HTTP (80)
resource "google_compute_firewall" "allow_spring_8080" {
  name    = "allow-spring-8080-tf"
  network = "default"

  allow {
    protocol = "tcp"
    ports    = ["80", "8080"]
  }

  source_ranges = ["0.0.0.0/0"]
  target_tags   = ["spring-app"]
}

# 4. Provision a Standard Regional Cloud Storage Bucket
resource "google_storage_bucket" "app_bucket" {
  name          = "ivory-link-spring-artifacts-2026"
  location      = "US-CENTRAL1"
  storage_class = "STANDARD"
  uniform_bucket_level_access = true
}

# 5. Output the VM's Public IP Address after deployment
output "vm_external_ip" {
  value = google_compute_instance.tf_vm.network_interface[0].access_config[0].nat_ip
}

3. The 4-Phase Terraform Lifecycle & Saved Plans (-out=tfplan)

Phase / Command What It Executes Under the Hood
terraform init Scans .tf files, identifies the google provider, and downloads the official GCP plugin binaries into .terraform/.
terraform plan Compares desired .tf code against terraform.tfstate and live GCP APIs. Outputs a speculative preview diff without modifying resources.
terraform plan -out=tfplan Saves a frozen binary execution blueprint to disk. Guarantees terraform apply tfplan executes exact reviewed actions without re-calculating or prompting yes. (Warning: contains cleartext state variables—never commit tfplan to Git!).
terraform apply Executes API calls against Google Cloud to create, update, or replace infrastructure and updates terraform.tfstate.
terraform destroy Reads the state file and cleanly tears down every managed resource in reverse dependency order to guarantee $0 billing.

4. Inside terraform.tfstate & Understanding Plan Diffs

When Terraform provisions your VM, it records the real-world GCP resource ID, lineage, and attributes inside terraform.tfstate. During subsequent runs, Terraform compares your code to this file and uses four diff symbols:

  • + (Create): Resource exists in code but not in state; will be newly created.
  • ~ (Update in-place): Attribute changed (e.g., adding network tags) and can be modified live without rebooting.
  • - (Destroy): Resource was removed from code and will be deleted from GCP.
  • -/+ (Destroy and Recreate): Immutable property changed (e.g., changing VM name or boot disk OS image), forcing replacement.
JSON — terraform.tfstate SNIPPET 
{
  "version": 4,
  "terraform_version": "1.9.0",
  "serial": 3,
  "resources": [
    {
      "mode": "managed",
      "type": "google_compute_instance",
      "name": "tf_vm",
      "instances": [
        {
          "attributes": {
            "id": "projects/ivory-link-511508-u3/zones/us-central1-a/instances/my-first-tf-vm",
            "machine_type": "e2-micro",
            "status": "RUNNING",
            "tags": ["http-server", "spring-app"]
          }
        }
      ]
    }
  ]
}
DIFF — IN-PLACE UPDATE (~) PREVIEW 
Terraform will perform the following actions:

  # google_compute_instance.tf_vm will be updated in-place
  ~ resource "google_compute_instance" "tf_vm" {
        id   = "projects/ivory-link-511508-u3/zones/us-central1-a/instances/my-first-tf-vm"
        name = "my-first-tf-vm"
      ~ tags = [
          + "http-server",
          + "spring-app",
        ]
        # (17 unchanged attributes hidden)
    }

Plan: 0 to add, 1 to change, 0 to destroy.
