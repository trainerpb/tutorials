Kafka Producer Mastery

Acks, Partitioning, and Idempotency

Producer Acknowledgments (acks)

The acks configuration dictates how many broker replicas must acknowledge a message before the producer considers the write successful. It is a direct trade-off between latency and durability.

acks=0 (Fire and Forget)

The producer sends the message and does not wait for a response from the broker. Retries cannot occur because the producer never knows if the write failed.

  • Pros: Maximum possible throughput, lowest latency.
  • Cons: Highest risk of data loss. If the broker is down or the network drops the packet, the message is gone permanently.
  • Use Case: High-volume telemetry or log aggregation where losing a few data points is acceptable.

acks=1 (Leader Acknowledgment)

The producer waits for the Leader broker of the partition to write the record to its local disk and return an ACK. It does not wait for Follower replicas to copy it.

  • Pros: Good balance of latency and safety.
  • Cons: Edge case data loss. If the Leader broker crashes immediately after sending the ACK but before the Followers replicate the data, the new elected Leader will not have the message.

acks=all or acks=-1 (Highest Durability)

The producer waits for the Leader AND all in-sync replicas (ISRs) to successfully write the message. (Must be paired with broker config min.insync.replicas=2).

  • Pros: Zero data loss as long as the minimum number of in-sync replicas remain alive.
  • Cons: Highest latency, as it must wait for network replication.
  • Use Case: Financial transactions, billing, core business events.

Routing & Partitioning Strategies

A Kafka topic is split into partitions. The Producer's Partitioner class decides which partition a message goes to. This is crucial for load balancing and strict ordering.

1. The Default Partitioner (Key-Hash)

If you provide a Key (e.g., userId, orderId), the default partitioner hashes the key using MurmurHash2 and mods it by the number of partitions.

Effect: All messages with the identical key will ALWAYS be routed to the exact same partition. Since Kafka guarantees ordering within a single partition, all events for a specific user are processed sequentially.

2. Sticky Partitioner (Null Key)

If you do NOT provide a key, old Kafka versions used Round-Robin (P0, P1, P2, P0...). This was inefficient because it created many small network batches.

Modern Kafka (2.4+) uses the Sticky Partitioner. It "sticks" to a single partition until a batch is full or linger.ms expires, sends the large batch to that partition, and then randomly selects a new partition for the next batch. This drastically reduces CPU and network overhead.

Spring Boot Implementation

spring:
  kafka:
    producer:
      acks: all
      properties:
        linger.ms: 5 # Wait 5ms to build larger batches
        enable.idempotence: true

The Duplicate Problem & Idempotent Producer

Network unreliability creates a specific edge case for producers: The Lost ACK.

The Scenario

  1. Producer sends Message A to the Broker.
  2. Broker successfully writes Message A to disk.
  3. Broker sends an ACK back to the Producer.
  4. The network drops the ACK packet.
  5. Producer times out, assumes the write failed, and retries sending Message A.
  6. Broker writes Message A again. You now have duplicate data!

The Solution: enable.idempotence=true

When you enable idempotence (which is the default in Kafka 3.0+), the Producer does two things automatically under the hood:

  • Producer ID (PID): Upon startup, the producer asks the broker for a unique ID.
  • Sequence Number: Every message the producer sends includes a sequence number (0, 1, 2, 3...).

If an ACK is lost and the producer retries Sequence #0, the Broker checks its memory. It sees, "I already have Sequence #0 from this PID." The broker safely discards the duplicate write and re-sends the ACK. Exactly-once state is preserved.

Real-World Emulation: Toxiproxy

To tangibly see the effects of a lost ACK in a local environment, you need a network chaos tool. Toxiproxy (built by Shopify) sits between your Spring Boot app and the Kafka broker.

1. Docker Compose Setup

services:
  kafka:
    image: bitnami/kafka:latest
    ports: ["9092:9092"]
  toxiproxy:
    image: shopify/toxiproxy
    ports: ["8474:8474", "9093:9093"] # 9093 is the proxy port

Configure Spring Boot to connect to localhost:9093 (the proxy), NOT 9092 (the broker directly).

2. Injecting Chaos (The Lost ACK)

Use the Toxiproxy CLI or REST API to add a timeout toxic. This rule allows the producer's request packet to reach the broker, but blocks the broker's return ACK packet.

# Drop data coming *from* Kafka (downstream) to simulate a lost ACK
toxiproxy-cli toxic add -t timeout -d downstream -a timeout=0 kafka_proxy

If enable.idempotence=false, you will see duplicates in your consumer logs. If true, the broker will block the duplicate.
