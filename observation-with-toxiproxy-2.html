Kafka Deep Dive Summary

1. The Advertised Listeners Bypass Trap

The Illusion: Traffic appears to bypass Toxiproxy completely after the first successful metadata fetch.

The Reality: Kafka clusters hand out routing instructions. When Spring Boot asks the broker (via Toxiproxy at 19092) for partition leaders, the broker replies with its default EXTERNAL address (localhost:9092). Spring Boot caches this and sends all subsequent payloads directly to the broker, effectively circumventing the chaos proxy.

The Fix: The broker's KAFKA_ADVERTISED_LISTENERS must be hardcoded to tell external clients to communicate strictly over the Toxiproxy port (EXTERNAL://localhost:19092).

2. The Metadata Primer vs. Delivery Umbrella

The Illusion: A 10-second delivery.timeout.ms kill switch hangs for 60 seconds.

The Reality: The delivery.timeout.ms overarching timer does not start until a payload successfully enters the RecordAccumulator buffer. If the producer does not have topic metadata cached, it must fetch it over the network first. If the network drops during this metadata fetch, the payload is stuck outside the buffer on the application thread. It waits for the max.block.ms timer (default 60s) to expire before throwing a TimeoutException: Topic not present in metadata.

The Rule: To accurately test network flight timeouts, you must "prime the pump" by sending one successful message to cache the metadata before activating network blackholes.

3. The Garbage Collection Tax (Dynamic Allocation)

The Illusion: Payloads larger than batch.size but smaller than buffer.memory cause no errors and are sent successfully.

The Reality: Kafka bypasses the standard, highly-efficient pre-allocated memory pool for these messages. It dynamically allocates a one-off chunk of unpooled RAM specifically for the giant payload, sends it, and instantly orphans the memory chunk. Under high throughput, this triggers severe JVM Garbage Collection spikes and CPU thrashing.

4. Buffer Exhaustion Triggers

The Mechanism: BufferExhaustedException is a strict, edge-case error. It only occurs if buffer.memory is 100% full AND max.block.ms is explicitly set to 0. If max.block.ms is greater than zero, the producer politely pauses the calling thread to wait for space. If the stopwatch hits zero, it throws a generic TimeoutException instead.

Toxiproxy CLI Command Structure

The Toxiproxy CLI utilizes a consistent syntax pattern for injecting "toxics" (network degradation conditions) into active proxy routes.

./toxiproxy-cli toxic add -n [NAME] -t [TYPE] -a [KEY=VALUE] -[DIRECTION] [PROXY_NAME]

Parameter Breakdown

  • -n (Name): A custom label (e.g., ack_blackhole) used to target and delete this specific toxic later.
  • -t (Type): The behavior to inject (latency, bandwidth, timeout, limit_data, slicer).
  • -a (Attribute): The mathematical value for the toxic behavior (e.g., latency=15000).
  • -d / -u (Direction): Boolean flags. -d applies the effect to downstream traffic (Broker to Client), while -u applies to upstream traffic (Client to Broker).
  • Proxy Name: The target routing tunnel established in the daemon (e.g., kafka-proxy).
